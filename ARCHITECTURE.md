# Архитектура решения «Граф денег»

Статус: офлайн-MVP реализован. Фактические формулы, пороги, ограничения и результаты —
README.md и config.yaml. Расширенные метрики ниже остаются проектными, если не указаны в README.
Рекомендуемый объём и уточнённые определения —
[DECISIONS.md](DECISIONS.md), порядок работ — [PLAN.md](PLAN.md).
Расширенный ИИ-слой ниже описывает возможное развитие; для MVP он не требуется.

Два слоя с жёсткой границей:

- **Ядро — детерминированное.** Python, pandas, networkx. Считает метрики, присваивает роли
  по документированным правилам, кластеризует, ранжирует, пишет 3 CSV. Работает офлайн,
  без ключей. Цель проверки: одинаковые CSV при одинаковых входе, конфигурации,
  порядке вычислений и зафиксированных версиях зависимостей.
- **Слой ИИ — надстройка.** Агенты с ролями работают **поверх уже посчитанных чисел**:
  пишут обоснования на языке аналитика, формулируют гипотезы кластеров, проверяют осторожность
  формулировок, отвечают на вопросы аналитика. Включается флагом `--llm`.

> Граница принципиальная. ТЗ запрещает «чёрный ящик»: роль без объяснимого правила не
> засчитывается. Поэтому **модель никогда не присваивает роль и не считает числа** — она только
> превращает готовые числа в текст. Это же снимает вопрос воспроизводимости: жюри запускает
> пайплайн без ключа OpenAI и получает все три выгрузки.

## Стек

- Python 3.12+, pandas, pyarrow, networkx, numpy (проверено на 3.13)
- Визуализация: Streamlit + pyvis (граф) — один экран, локальный запуск
- Слой ИИ: OpenAI API, опционально, через флаг
- Запуск локальный, деплоя нет, проект живёт в git

## Метрики узла

Базовые (уже есть в `starter.py`): `in_deg`, `out_deg`, `in_kzt`, `out_kzt`, `in_tx`, `out_tx`,
`pagerank`, `pass_through`, `depth`, `is_seed`, `truncated_by_depth`.

Добавляем:

| Метрика | Зачем |
|---|---|
| `hub` / `authority` (HITS) | разделяет «рассылающих» и «собирающих» — прямо под distributor / consolidator |
| `betweenness` | в MVP — невзвешенное направленное посредничество; денежная сумма не используется как длина пути |
| `in_concentration` | максимальная сумма от одного входящего контрагента / `in_kzt`; при нулевом входе не определена |
| `avg_in_tx` / `avg_out_tx` | средний размер перевода — ловушка №3 ТЗ: суммы и количество это разные сигналы |
| `n_seed_sources` | от скольких seed деньги доходят до узла. Чем больше, тем интереснее следствию |
| `hold_days` | медианная временная близость входящих к последующим исходящим; определение и ограничения в DECISIONS.md |
| `same_day_inflows` | сколько разных плательщиков заплатили в один день — синхронность |
| `cut_risk` | падение связности компоненты при удалении узла — устойчивость сети |

Стартовый код найден и скопирован в starter/. Он загружает transactions для проверки
входа; временные признаки остаются опциональным расширением после приёмки MVP.

## Правила ролей: скоринг, а не каскад if-else

Для каждого узла сначала проверяем допустимость специализированных ролей, затем считаем
их скоры. Если максимальный допустимый скор ниже порога, назначаем `peripheral`.
Иначе выбираем максимум с фиксированным порядком равенств. `role_score` — эвристический
балл соответствия правилу, не измеренная вероятность. Шкала fallback, нормировки,
пороги и веса должны быть формально определены в config.yaml при реализации.

Почему так, а не цепочка условий:
- каждый узел получает роль всегда — нет «провалов» между правилами;
- `role_score` появляется естественно, а не назначается вручную;
- виден второй кандидат — можно сказать жюри «это transit со скором 0.72, но почти
  consolidator, 0.68, вот почему»;
- правило остаётся читаемым: скор = взвешенная сумма 2–3 понятных признаков.

Ориентиры порогов из примечания ТЗ (по ним проверяем, что не промахнулись):

| Роль | Основные признаки | Что ожидаем увидеть |
|---|---|---|
| `consolidator` | `in_deg` высокий, `in_concentration` низкая, `pass_through` < 0.6 | узлы с входящими от **8–24** разных плательщиков |
| `distributor` | `out_deg` высокий, `hub` высокий | веер на **60–116** получателей |
| `transit` | `pass_through` в **0.8–1.2**, `hold_days` мал, есть и вход и выход | около **72** узлов |
| `terminal` | `out_deg == 0`, **`truncated_by_depth == False`**, `in_kzt` значим | см. ловушку ниже |
| `coordinator` | `betweenness` высокий, `n_seed_sources` высокий, `depth` ≥ 2 | единицы узлов |
| `peripheral` | ни один скор не превысил минимальный порог | основная масса |

Эти числа — диагностические ориентиры свойств данных, не разметка ролей и не приёмочный
тест их количества. Расхождения требуют анализа метрик и правил; подгонять ответ нельзя.

### Ловушка обрыва — отдельная колонка, а не молчание

444 узла на 4-м колене без исходящих. Наивно назвать их `terminal` — дать 444 ложных вывода.

Решение:
1. `terminal` присваивается только при `truncated_by_depth == False`.
2. Для обрезанных узлов не используем отсутствие исходящих как свидетельство накопления.
   Роль оцениваем только по допустимым наблюдаемым признакам; снижение скора само по себе
   не исправляет недостоверный признак. Недостаточные признаки ведут к fallback.
3. Добавляем **необязательную колонку `data_limitation`** со значением
   `truncated_at_hop_4` — лишние колонки ТЗ разрешает.
4. `evidence` у таких узлов прямо говорит: «обход завершён на 4-м колене, исходящие переводы
   могут существовать вне выгрузки — требуется дозапрос».

Пункт 4 одновременно закрывает опциональный пункт «оценка полноты»: из этих же узлов
собирается список того, что аналитику стоит запросить следующим (`src/gaps.py`).

### Ловушка seed

У seed входящие занижены по построению выгрузки. Поэтому `pass_through` и всё, что от него
зависит, для `is_seed == True` либо не используется, либо используется с явной оговоркой
в `evidence`. Роль seed определяется по исходящим признакам.

## Кластеры

Louvain на неориентированной проекции с весом `sum_kzt`. В README явно оговариваем, что проекция
неориентированная и почему это допустимо для задачи «кто с кем связан» — ловушка №4 ТЗ.

Встречные рёбра суммируются. Изоляты получают отдельные кластеры. Фиксируем seed алгоритма,
порядок входа и стабильную нумерацию. Внутренний оборот считаем по исходным направленным рёбрам.

По каждому кластеру: `n_nodes`, `n_seed`, `sum_kzt_internal`, `top_gids`, `hypothesis`.
Гипотеза — шаблонная из состава ролей кластера («12 узлов, 4 seed, две точки консолидации,
оборот 18 млн — признаки самостоятельной ветки сбора»), с `--llm` переписывается агентом.

Ориентир из ТЗ: **8 сообществ** с более чем одним seed при базовой кластеризации.
Это не требование получить ровно восемь; устойчивость нашего результата нужно измерять отдельно.

## priority_score: ответ на главный вопрос кейса

Вопрос аналитика — «кого смотреть первым». Скор собирается из четырёх понятных слагаемых
с весами из `config.yaml`:

```
priority = w1 · вес_роли(role)          # coordinator и consolidator выше курьеров
         + w2 · норм(n_seed_sources)    # сколько известных фигурантов сходится на узел
         + w3 · норм(in_kzt)            # объём прошедших денег
         + w4 · норм(betweenness)       # направленное посредничество
```

В MVP cut_risk не используется. Если добавляем его позднее, явно меняем формулу и
помечаем узлы, для которых метрика не вычислена; неизвестное значение не заменяем нулём.

Каждое слагаемое — число, которое видно в карточке узла. На защите на вопрос «почему этот gid
первый» отвечаешь разложением скора по слагаемым, а не «так модель решила».

## Экран просмотра (Streamlit)

Один экран, четыре зоны:

1. **Схема сети** — pyvis. Весь граф из 2 248 узлов рисовать бессмысленно: показываем
   топ-N по приоритету плюс их связи, цвет = роль, толщина ребра = сумма, стрелка = направление.
2. **Поиск по gid** — требование must-have 5: жюри называет gid, находим и показываем связи.
   По gid строится эго-граф на 1–2 колена.
3. **Карточка узла** — роль, скор, все метрики, evidence, соседи, что дозапросить.
   Закрывает опциональный пункт «автогенерация карточки узла».
4. **Топ-20** — таблица с обоснованием, клик по строке открывает карточку.

Три обязательных CSV не содержат рёбер. Тот же прогон дополнительно экспортирует
viewer_edges.parquet, node_features.parquet и run_manifest.json. Интерфейс читает
согласованные артефакты одного прогона. Изоляты видны, при ограничении числа соседей
показываем уведомление и полный табличный список. Граф использует локальные ресурсы.

## Возможное развитие: пять агентов

Включается флагом `--llm`, работает поверх готовых чисел. Без флага пайплайн полный.

| Агент | Роль | Вход | Выход |
|---|---|---|---|
| `EvidenceWriter` | превращает метрики узла в обоснование на языке аналитика | строка метрик | `evidence`, ≤200 символов |
| `ClusterAnalyst` | формулирует гипотезу назначения кластера | сводка кластера | `hypothesis` |
| `PriorityExplainer` | объясняет позицию в топ-листе | разложение priority_score | `why` |
| `ComplianceCritic` | **проверяет осторожность формулировок** | любой текст выше | вердикт + правка |
| `AnalystAssistant` | вопрос на естественном языке → ответ по графу | вопрос + инструменты | ответ со ссылками на gid |

**`ComplianceCritic` — не украшение.** ТЗ прямо требует: «выводы формулируются как гипотезы
для проверки, а не как утверждение о виновности». Критик отклоняет тексты вида «узел отмывает
деньги» и возвращает на переписывание в «признаки консолидации, требует проверки». В интерфейсе
можно показать отклонённый и исправленный вариант. Специально подготовленный пример
обозначается как тестовый; обязательное наличие отказа в реальном прогоне не требуется.
Критик не гарантирует корректность: отдельно проверяем gid, числа и схему ответа,
при ошибке возвращаем шаблон. Для первой версии достаточно одного ИИ-сценария.

**`AnalystAssistant`** закрывает опциональный пункт 6. Инструменты (`src/ai/tools.py`) —
функции по графу: найти пути между узлами, получить соседей, отфильтровать по роли, посчитать
поток. Модель их вызывает, но не считает сама.

Связь между агентами задаётся полем `consumes`; из него строится и порядок выполнения,
и схема в README.

## Производительность

Ограничение ТЗ — полный пересчёт **≤ 5 минут**. На 2 248 узлах основные метрики считаются
секунды. Следить за двумя местами:

- `betweenness_centrality` на 2 248 узлах — терпимо, но при необходимости брать
  `k`-сэмплирование и указать это в README;
- `simple_cycles` — ограничивать `length_bound=6`, иначе взрывается.

Слой ИИ при `--llm` — это ~2 300 вызовов, если писать evidence каждому узлу. Так делать
нельзя: модель вызывается **только для топ-N узлов и кластеров**, остальным идёт шаблонный
текст. Это и быстрее, и честнее — обоснование для периферийного узла всё равно шаблонное по сути.

## Масштабирование до ~1 млн узлов (нужно в README, реализация не требуется)

Текстом: pandas → Polars или DuckDB; networkx → igraph или graph-tool; PageRank и Louvain
через распределённые реализации; betweenness только на сэмпле; хранение графа в колоночном
формате с партиционированием по времени; пересчёт инкрементальный — по новым рёбрам,
а не всей сети.
