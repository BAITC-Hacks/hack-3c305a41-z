# Задачи для Codex — кейс «Граф денег»

Готовые промпты по таймлайну из `PLAN.md`. Копируются в Codex как есть.

Формат каждой задачи — по рекомендации OpenAI: **цель → что сделать → ограничения →
критерий готовности → файлы через `@`**. Ссылки на конкретные файлы ограничивают правки
и повышают точность.

---

## Как передать Codex контекст

1. **Создать репозиторий** и скопировать в него:
   - `AGENTS.md` → в **корень** (Codex подхватывает сам при каждой задаче)
   - `CASE-TZ.md`, `CASE.md`, `ARCHITECTURE.md`, `PRODUCT.md`, `DEMO.md` → в `docs/`
   - `data/` и `starter/` от организаторов → в корень
2. **Первая задача — №0** ниже.
3. **Дальше ссылаться на документы через `@`**: `@docs/ARCHITECTURE.md`, `@docs/CASE.md`.
   Не пересказывать их содержимое в промпте — появятся два источника правды.
4. **README не оставлять на конец.** Это 25 баллов из 100, столько же, сколько вся техническая
   реализация. Обновлять после каждой задачи.

## 1. Расширенные метрики (T+0:30–1:15)

```
Цель: досчитать метрики из раздела "Метрики узла" @docs/ARCHITECTURE.md.

Сделай в src/features.py:
- hub и authority через nx.hits
- betweenness_centrality, взвешенный, с параметром k из config.yaml для сэмплирования
- in_concentration: доля крупнейшего входящего платежа в in_kzt
- avg_in_tx, avg_out_tx
- n_seed_sources: от скольких seed-узлов достижим данный узел по направленным путям
- cut_risk: рост числа слабосвязных компонент при удалении узла (считать только
  для топ-N по pagerank, остальным 0 — иначе не уложимся в 5 минут)

Сделай в src/temporal.py на основе transactions.parquet:
- hold_days: медиана времени между входящим и последующим исходящим переводом
- same_day_inflows: максимальное число разных плательщиков за один день

Ограничения:
- полный прогон обязан оставаться в пределах 5 минут, замерь и выведи время каждого шага
- метрики, которые недостоверны для seed, пометь в коде комментарием
- все параметры расчёта — в config.yaml

Критерий готовности: python run.py отрабатывает < 5 минут, все метрики посчитаны
без NaN там, где они не ожидаются; распределения метрик выведены в консоль.

Файлы: @docs/ARCHITECTURE.md @src/features.py @config.yaml
```

## 2. Роли и скоры (T+1:15–2:15) — ядро решения

```
Цель: присвоить каждому из 2248 узлов роль из словаря ТЗ с обоснованием.

Реализуй в src/roles.py подход из раздела "Правила ролей" @docs/ARCHITECTURE.md:
считаем шесть скоров по нормированным признакам, роль = argmax, role_score = значение
победившего скора. Второй по величине скор сохраняем отдельной колонкой role_runner_up.

Роли и признаки — таблица в @docs/ARCHITECTURE.md. Пороги и веса — только в config.yaml,
каждый с комментарием, почему он такой.

Обязательно учти две ловушки:
- terminal присваивается только при truncated_by_depth == False. Для узлов с depth==4
  и нулевыми исходящими role_score умножается на понижающий коэффициент, добавляется
  колонка data_limitation со значением truncated_at_hop_4
- у seed занижены входящие, поэтому pass_through для них недостоверен: роль seed
  определяется по исходящим признакам, в evidence это оговаривается

Реализуй в src/narrate.py шаблонные evidence: до 200 символов, с конкретными числами,
формулировка как гипотеза ("признаки консолидации: получает от 11 разных плательщиков,
передаёт дальше 3% полученного"), без утверждений о виновности.

Ограничения:
- никаких списков gid в коде
- работает офлайн, без обращений к модели

Критерий готовности: nodes_roles.csv заполнен на 2248 строк. Проверь распределение ролей
против ориентиров из примечания ТЗ (@docs/CASE.md, раздел "Что точно есть в данных"):
узлы с входящими от 8-24 плательщиков должны становиться consolidator, узлы с веером
на 60-116 получателей — distributor, около 72 узлов с пропуском 0.8-1.2 — transit.
Выведи в консоль таблицу "роль → количество узлов" для проверки.

Файлы: @docs/ARCHITECTURE.md @docs/CASE.md @src/features.py @config.yaml
```

Файлы: @docs/ARCHITECTURE.md @src/roles.py @config.yaml

## 5. Слой агентов (T+3:50–4:20)

```
Цель: реализовать слой из раздела "Слой ИИ" @docs/ARCHITECTURE.md под флагом --llm.

src/ai/agents.py — пять агентов с ролями, промптами и схемами ответа:
EvidenceWriter, ClusterAnalyst, PriorityExplainer, ComplianceCritic, AnalystAssistant.
Связи между ними задаются полем consumes.

src/ai/orchestrator.py — порядок выполнения из consumes, параллельные вызовы,
одна итерация возврата текста от ComplianceCritic автору.

ComplianceCritic проверяет каждый текст на осторожность формулировок по требованию ТЗ:
отклоняет утверждения о виновности, возвращает на переписывание в форму гипотезы.
Отклонённый и исправленный вариант сохраняются в лог — их показывают на демо.

src/ai/tools.py — функции по графу для AnalystAssistant: соседи узла, пути между двумя
узлами, фильтр по роли, суммарный поток. Модель вызывает их, но не считает сама.

Ограничения:
- модель вызывается только для топ-N узлов и кластеров, не для всех 2248 узлов
- без флага --llm пайплайн работает ровно как раньше и не обращается к сети
- модель не присваивает роли и не меняет числа, только переписывает текст
- ключ читается из переменной окружения

Критерий готовности: python run.py --data data --out out проходит без ключа;
с ключом и флагом --llm тексты в CSV становятся содержательнее, в логе виден
хотя бы один случай возврата текста критиком.

Файлы: @docs/ARCHITECTURE.md @src/narrate.py @AGENTS.md
```
